### 1.2 Regras de negócio (US-02.5)

- **Identidade:** no backlog, a identidade e o perfil do usuário vêm de um sistema externo e a plataforma não os cadastra. Até isso ser definido com o cliente (ver seção 6), o login `POST /api/v1/auth/login` é **provisório**: valida e-mail e senha contra usuários declarados em configuração.
- **Papéis oficiais:** `analista` e `gestor` (valores exatos no token).
- **Escopo:** nesta US, o escopo do usuário é **uma rede**. A regra "escopo do usuário ⊇ escopo da campanha" se resume a "a rede da operação é a rede do usuário".
- **Fora do escopo:** a operação é recusada com `403` e a mensagem exata do backlog: **"Escopo organizacional fora da sua permissão de acesso"**.
- **Alçada:** só o gestor aprova (PR-05). Esta US entrega as policies por papel; a regra é aplicada quando o endpoint de aprovação existir (US-01.11).
- **Isolamento na consulta (cenário 3):** esta US entrega o acesso ao usuário atual (`ICurrentUser`); o filtro por rede é aplicado nas consultas das US que as criarem (US-01.9).

### 1.3 Contrato de erros (US-07.5, cenários 2 e 3)

Todas as respostas de erro da API seguem `ProblemDetails` com a extensão `code`, sem expor detalhes internos (stack trace, nomes de classes, SQL):

| Situação | HTTP | `code` | `detail` |
|---|---|---|---|
| Corpo ou campos inválidos (erro de contrato) | 400 | `VALIDATION_ERROR` | "A requisição contém campos inválidos." (+ `errors` por campo) |
| Login com credenciais inválidas ou inexistentes | 401 | `AUTH_INVALID_CREDENTIALS` | "Credenciais inválidas." |
| Rota protegida sem token, com token inválido ou expirado | 401 | `AUTH_UNAUTHENTICATED` | "Autenticação necessária." |
| Papel sem permissão para a operação | 403 | `AUTH_FORBIDDEN_ROLE` | "Seu papel não permite esta operação." |
| Operação fora do escopo organizacional | 403 | `SCOPE_FORBIDDEN` | "Escopo organizacional fora da sua permissão de acesso" |

- **Convenção para as próximas US:** erro de contrato → `400 VALIDATION_ERROR`; violação de regra de negócio → `422` com `code` próprio da regra (ex.: `CAMPAIGN_INVALID_PERIOD` na US-01.1). Assim o satélite e o frontend distinguem os dois casos, como pede a US-07.5.
- Respostas `401` de rotas protegidas incluem `WWW-Authenticate: Bearer`.

### 1.4 Configuração

| Chave | Obrigatória | Regra |
|---|---|---|
| `Auth:Jwt:SigningKey` | Sim | Mínimo de 32 caracteres (HMAC-SHA256) |
| `Auth:Jwt:Issuer` | Sim | Não vazia; validada no token |
| `Auth:Jwt:Audience` | Sim | Não vazia; validada no token |

| `Auth:MockUsers` | Não | Lista de usuários provisórios; vazia = nenhum login aceito |

- `appsettings.json` traz só `Issuer`, `Audience` e `ExpirationMinutes`. A `SigningKey` de desenvolvimento e os `MockUsers` ficam em `appsettings.Development.json`. Em outros ambientes, a chave vem de `Auth__Jwt__SigningKey` (variável de ambiente ou `.env`).

## 2. Contratos & Schemas (DTOs / Records)

```csharp
// Application/Authentication
// Atributos no parâmetro (sem "property:"): o MVC valida records posicionais pelo construtor.
public record LoginRequest(
    [Required, EmailAddress] string Email,
    [Required] string Password);

// Contrato atual mantido (o frontend pode já consumi-lo).
public record TokenResponse(string Token, int ExpiresIn, string Message);

public interface IAuthService
{
    /// <returns>null quando as credenciais são inválidas.</returns>
    TokenResponse? Authenticate(LoginRequest request);
}

/// <summary>Fonte das credenciais. Hoje: configuração. Amanhã: projeção local ou sistema externo (seção 6).</summary>
public interface IUserCredentialStore
{
    UserAccount? FindByCredentials(string email, string password);
}

public record UserAccount(Guid UserId, string Email, string Role, Guid NetworkId);

public static class Roles
{
    public const string Analista = "analista";
    public const string Gestor = "gestor";
}

/// <summary>Usuário autenticado da requisição atual.</summary>
public interface ICurrentUser
{
    Guid UserId { get; }
    string Role { get; }
    Guid NetworkId { get; }
}

/// <summary>Implementado pelos requests cuja operação pertence a uma rede (ex.: CreateCampaignRequest na US-01.1).</summary>
public interface INetworkScopedRequest
{
    Guid NetworkId { get; }
}
```

## 3. Especificação do Endpoint / Serviço

### `POST /api/v1/auth/login`

- **Autenticação:** pública (`[AllowAnonymous]`).
- **Respostas:**
  - `200`: `TokenResponse` com o JWT, `ExpiresIn` em segundos e `Message = "Autenticação realizada com sucesso."`.
  - `400`: `VALIDATION_ERROR` (e-mail ou senha ausentes, e-mail mal formado).
  - `401`: `AUTH_INVALID_CREDENTIALS`, igual para e-mail inexistente e senha errada.
- E-mail comparado sem diferenciar maiúsculas; senha comparada em tempo constante.

### AuthGuard (autenticação JWT)

- Esquema `JwtBearer` validando assinatura, `iss`, `aud` e expiração (`ClockSkew` de 1 minuto).
- Os eventos `OnChallenge` e `OnForbidden` escrevem os `ProblemDetails` da seção 1.3.
- `GET /health`, `GET /api/v1/system/status` e `POST /api/v1/auth/login` continuam públicas.

### TenantGuard (`ValidateTenantScopeAttribute`, reescrito)

- Filtro de ação aplicado nas rotas que operam sobre uma rede.
- Lê a rede da operação, nesta ordem:
  1. argumento de rota ou query chamado `networkId`;
  2. argumento da ação que implemente `INetworkScopedRequest`.
- Se a rede da operação for diferente de `ICurrentUser.NetworkId` → `403 SCOPE_FORBIDDEN`.
- Se a ação não tiver rede identificável, o filtro falha com erro de programação (`InvalidOperationException`), para que o uso indevido apareça nos testes em vez de liberar o acesso.
- Escopos de região e estabelecimento (ex.: "campanha vinculada à região Nordeste da rede") dependem de consultar o banco e ficam para a US-02.3 (seção 6).

### `ICurrentUser`

- Implementado na Api a partir do `HttpContext.User` (claims `sub`, `role`, `escopoId`), registrado como `Scoped`.

## 6. Pontos de Atenção Futuros

- **Contas de usuário (dúvida em aberto com o cliente):** o backlog diz que a identidade vem de sistema externo, mas a plataforma terá usuários analista e gestor, possivelmente importados ("parsing") do sistema do cliente. Falta definir:
  - se os usuários serão importados para uma tabela própria (projeção local), sincronizados ou autenticados direto no sistema do cliente (SSO/OIDC);
  - quem cadastra, inativa e troca papel ou escopo de um usuário.

  A troca não é destrutiva: basta uma nova implementação de `IUserCredentialStore` (ou a substituição do login por um provedor externo), sem mudar `ICurrentUser`, as policies nem o TenantGuard. Se houver senha local, ela deve ser gravada com hash (ex.: `PasswordHasher<T>`), nunca em texto.
- **Projeção local de usuários:** a US-02.5 exige identificador, papel e escopo guardados localmente para a alçada e a auditoria de quem submeteu e aprovou (US-01.6, US-01.11, EP-03). Entra junto com a decisão acima, no máximo até a US-01.6.
- **Granularidade do escopo:** hoje o escopo é só a rede. Escopos por região ou estabelecimento, e a validação de que a região ou loja da campanha pertence à rede do usuário, ficam para a US-02.3.
- **Alçada e isolamento na consulta:** aplicados nas US-01.11 (aprovar) e US-01.9 (consultar) com as peças desta spec.
- **US-07.5 real:** autenticar aplicações satélites (ex.: client credentials ou API key) e registrar o identificador da aplicação na auditoria fica para o EP-07. Esta spec só adianta o contrato de erros.
- **Sessão:** sem refresh token e sem revogação de token nesta fase; o token expira em `Auth:Jwt:ExpirationMinutes` e o frontend deve tratar `401 AUTH_UNAUTHENTICATED` voltando ao login. Motivo: nenhum requisito pede, o login é provisório (com SSO o refresh seria do provedor de identidade) e um refresh token seguro exige estado no servidor (armazenamento, rotação e revogação) ligado a usuários persistidos, que ainda não existem. Entra em spec própria junto com a projeção local de usuários.
- **Alinhamento com a equipe:** avisar o autor da implementação original (commit `56839cd`) e o frontend sobre a troca de `escopoId` para o `Guid` da rede, os novos usuários de teste e o formato `ProblemDetails` dos erros.
