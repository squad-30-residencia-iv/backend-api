## 1. Contexto & Regras de Negócio

- O `POST /api/v1/auth/login` passa a devolver o nome da pessoa em `profile.name`, para o portal deixar de exibir o e-mail na Home e na Sidebar.
- O nome fica na tabela `users` (`name`), obrigatório, de 1 a 150 caracteres, sem ir para o JWT. As claims continuam `sub`, `role` e, quando existe, `escopoId`.
- `Auth:MockUsers` exige `Name` de 1 a 150. Entrada ausente, vazia ou maior que 150 impede a subida com `Configuração inválida`.
- O seed grava o nome só quando `users` está vazia. Não reescreve uma linha já existente.
- A migração `UserName` cria `name` `NOT NULL` nos dois bancos. Linhas já gravadas recebem Ana Lima, Bruno Costa e Admin Plataforma para `analista@empresa.com`, `gestor@empresa.com` e `admin@empresa.com`. Qualquer outra linha recebe o próprio e-mail.
- Carga de Development: os mesmos três nomes.

## 2. Contratos & Schemas (DTOs / Records)

```csharp
public record UserAccount(Guid UserId, string Email, string Name, string Role, Guid? NetworkId);

public record UserProfileResponse(Guid UserId, string Email, string Name, string Role, Guid? NetworkId);
```

O JSON do perfil segue o camelCase já usado (`name`). `token`, `expiresIn` e `message` não mudam.

---

## 3. Especificação do Endpoint / Serviço

- Rota: `POST /api/v1/auth/login` (já existente; anônimo).
- O serviço lê `User.Name` pelo `DatabaseUserCredentialStore` e monta `UserProfileResponse` no `JwtAuthService`.
- Respostas HTTP:
  - 200: token e `profile` com `name`.
  - 401: credenciais inválidas, sem mudança (`AUTH_INVALID_CREDENTIALS`).
  - 400: contrato inválido, sem mudança.
