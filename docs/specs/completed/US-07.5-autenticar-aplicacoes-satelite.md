> Responsável: Gabriel Torres
> Data: 2026-11-09

## 1. Contexto & Regras de Negócio

- As aplicações satélites (PDV, e-commerce, app) vão chamar a concessão e o resgate (07.2, 07.3, 07.4). Elas precisam de credencial própria, separada do login de analista e gestor (US-02.5).
- Modelo **client credentials**: cada aplicação tem `clientId` e `clientSecret`, troca os dois por um token de curta duração e envia o token como `Authorization: Bearer`.
- Cada aplicação pertence a **uma rede** e tem uma lista de **escopos** (o que ela pode fazer). Rede errada → `403 SCOPE_FORBIDDEN`; escopo ausente → `403 AUTH_FORBIDDEN_SCOPE`.
- O token do usuário não abre rota de satélite, e o token da aplicação não abre rota de usuário: cada um tem sua audiência e seu esquema de autenticação.
- Erros no padrão EP-07 já usado na API: `ProblemDetails` com a extensão `code`.

### 1.1 Decisões

| # | Ponto | Decisão |
|---|---|---|
| D-1 | O texto do backlog (`epico_07.md`) não está no repositório. | Critérios tirados da issue #26 (seção F), do `ROADMAP.md` e da spec da US-02.5 (contrato de erros). Revisar com o dono do backlog. |
| D-2 | Credencial: client credentials ou API key. | Client credentials com JWT: o token expira (padrão 60 min), carrega rede e escopos e reaproveita a validação do JWT. A chave da aplicação não trafega em toda requisição. |
| D-3 | Onde ficam as aplicações. | Tabela `satellite_apps`, com o segredo só como hash PBKDF2, igual à senha em `users` (D5). `Auth:Satellite:Apps` é só a carga inicial quando a tabela está vazia. Sem chave estrangeira para `networks`, como em `users`. |
| D-4 | Separação dos tokens. | Mesmo emissor e chave de assinatura, audiência própria (`Auth:Satellite:Audience`, padrão `vouchercampaigns-satellite`) e esquema `Satellite`. O startup recusa audiência igual à do usuário. |
| D-5 | Escopos. | `campaigns:read` (07.1), `vouchers:issue` (07.2 / 07.4) e `vouchers:redeem` (07.3). No token, a claim `scope` é uma lista. |
| D-6 | Aplicação inativada com token ainda válido. | O token vale até expirar (sem revogação nesta fase). A aplicação inativa não recebe token novo. |
| D-7 | Rota de prova. | `GET /api/v1/satellite/me` devolve a aplicação do token, para o integrador conferir a credencial. As rotas do motor (issue #27) usam as policies de escopo. |

## 2. Contratos & Schemas

```csharp
public record SatelliteTokenRequest([Required] string ClientId, [Required] string ClientSecret);

public record SatelliteTokenResponse(
    string AccessToken,
    string TokenType,                // "Bearer"
    int ExpiresIn,                   // segundos
    IReadOnlyList<string> Scopes);

public record SatelliteAppResponse(
    Guid ApplicationId,
    string ClientId,
    Guid NetworkId,
    IReadOnlyList<string> Scopes);
```

Claims do token: `sub` (id da aplicação), `client_id`, `escopoId` (rede) e `scope` (lista). Sem `role`.

Tabela `satellite_apps`: `id`, `client_id` (100, único, minúsculo), `name` (150), `secret_hash` (200), `network_id`, `scopes` (200, separados por espaço), `is_active`, `created_at`.

Configuração (`Auth:Satellite`):

| Chave | Obrigatória | Regra |
|---|---|---|
| `Audience` | Não | Padrão `vouchercampaigns-satellite`; diferente de `Auth:Jwt:Audience` |
| `ExpirationMinutes` | Não | Padrão 60; maior que zero |
| `Apps:N:ClientId` | Sim, por app | Até 100 caracteres, sem espaço, único |
| `Apps:N:ClientSecret` | Sim, por app | Mínimo de 32 caracteres |
| `Apps:N:Name` | Sim, por app | Até 150 caracteres |
| `Apps:N:NetworkId` | Sim, por app | Guid |
| `Apps:N:Scopes` | Sim, por app | Ao menos um escopo conhecido |

Em Development, a aplicação `pdv-demo` da rede de demonstração já vem com os três escopos.

## 3. Especificação do Endpoint / Serviço

### `POST /api/v1/satellite/token`

- Pública. Corpo `SatelliteTokenRequest`.
- 200: `SatelliteTokenResponse`
- 400: `VALIDATION_ERROR` (campo ausente)
- 401: `AUTH_INVALID_CLIENT` "Credenciais da aplicação inválidas." (cliente inexistente, segredo errado ou aplicação inativa, sem diferenciar)

### `GET /api/v1/satellite/me`

- Policy `SatelliteApp` (esquema `Satellite`).
- 200: `SatelliteAppResponse`
- 401: `AUTH_UNAUTHENTICATED` (sem token, token de usuário, expirado ou assinado com outra chave)

### Policies para as rotas do motor

| Policy | Exige |
|---|---|
| `SatelliteApp` | Token de aplicação válido |
| `SatelliteReadCampaigns` | + escopo `campaigns:read` |
| `SatelliteIssueVouchers` | + escopo `vouchers:issue` |
| `SatelliteRedeemVouchers` | + escopo `vouchers:redeem` |

- Escopo ausente → `403 AUTH_FORBIDDEN_SCOPE` "A aplicação não tem permissão para esta operação."
- `[ValidateTenantScope]` usa a rede da aplicação quando quem chama é satélite → `403 SCOPE_FORBIDDEN`.
- Para saber qual aplicação está chamando: `ICurrentSatelliteApp` (`ApplicationId`, `ClientId`, `NetworkId`, `Scopes`).

## 5. Casos de Teste Essenciais

- [x] Credencial válida devolve token, e o token abre `GET /satellite/me` com aplicação, rede e escopos.
- [x] Segredo errado, cliente inexistente e aplicação inativa → `401 AUTH_INVALID_CLIENT`.
- [x] Corpo sem `clientSecret` → `400 VALIDATION_ERROR`.
- [x] `GET /satellite/me` sem token, com token de usuário, expirado ou com outra chave → `401 AUTH_UNAUTHENTICATED`.
- [x] Token de aplicação em rota de usuário (`GET /campaigns`) → `401`.
- [x] Rota que exige escopo ausente → `403 AUTH_FORBIDDEN_SCOPE`.
- [x] Rota de outra rede → `403 SCOPE_FORBIDDEN`.
- [x] Configuração inválida (segredo curto, rede inválida, escopo desconhecido, cliente repetido, audiência igual à do usuário) impede a subida.
